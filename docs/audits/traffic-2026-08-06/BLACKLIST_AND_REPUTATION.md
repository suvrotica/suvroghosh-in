The labels above and below are intentionally narrow:

- CLEAN — VERIFIED means the named service returned a documented negative result for the exact target at the stated time.
- LISTED — VERIFIED means the named service returned an explicit positive listing. No service produced this verdict in this audit.

- NOT APPLICABLE means the service is evidence about infrastructure or history, not a blacklist verdict.

## Infrastructure observations relevant to reputation

- Authoritative RDAP showed an active registration, registrar locks, and an expiry in 2032. There is no evidence of an expired-domain lapse.
- The live apex and www endpoints presented a trusted certificate covering the apex and wildcard, negotiated TLS 1.3, and were hostname-valid at 2026-08-06T12:56:56+05:30. The leaf expired on 2026-09-12 and therefore depended on normal automated renewal; there was no expiry problem at audit time.
- A public CT query exposed only the expected apex and wildcard names among currently unexpired certificates. This is useful anomaly evidence, not complete subdomain discovery.
- A synthetic, nonexistent subdomain resolved through the wildcard DNS configuration but served a generic 404 over HTTPS. No unexpected active application was found in that one safe probe. Wildcard DNS and certificates mean that this probe cannot establish that every possible subdomain is inactive.
- DNSSEC and CAA were absent. Those are hardening gaps, not blacklist evidence and not evidence of compromise.

## Delisting and review playbooks

Only use a playbook if its service later returns LISTED — VERIFIED. Preserve the evidence URL, detection name, first-seen time, affected URL, and screenshots before remediation.

### Google Safe Browsing / Search Console

1. Open Search Console's Security Issues report and inspect every example URL.
2. Remove the root cause across the entire site: compromised credentials, injected pages, malicious downloads, redirects, third-party scripts, or vulnerable software.
3. Confirm the deployed site is clean, rotate exposed credentials, invalidate sessions, and close the intrusion path.
4. Use the report's Request Review workflow, explaining the cause, the complete cleanup, and the preventive change. Google's [hacked-site reconsideration guidance](https://support.google.com/webmasters/answer/35843?hl=en) should be followed.
5. Treat a manual action separately in the Manual Actions report; fix all affected patterns before requesting reconsideration.

### VirusTotal

1. Obtain the owner-authorized domain view or API response and identify the exact engine that flags the domain.
2. Verify whether the engine has a real affected URL or a stale/false classification.
3. Clean the site first if the detection is valid. For a false positive, follow VirusTotal's [false-positive guidance](https://docs.virustotal.com/docs/false-positive) and contact the detecting vendor; VirusTotal aggregates vendor results.
4. Do not repeatedly request scans or upload repository/private material. Record the vendor's final response and recheck only after remediation.

### URLhaus

1. Use an owner-authorized session or API key to retrieve the exact URLhaus record.
2. If active, remove the malware payload and the mechanism that recreates it, then invalidate credentials and inspect adjacent URLs.
3. Use the record's documented false-positive/removal process if the listing is wrong. Preserve the record ID and submit only the minimum public URL evidence.
4. Distinguish an offline historical record from an active payload; neither should be silently translated into a whole-domain search penalty.

### Spamhaus DBL

1. Recheck the exact domain through [Spamhaus Blocklist Removal Center](https://check.spamhaus.org/) from an owner-controlled browser.
2. Follow the category-specific remediation, remove the abusive or compromised resource, and use the offered removal workflow.
3. Do not pay third-party “delisting” services. Spamhaus states that removal is free; some DBL entries expire after the condition clears.

### SURBL

1. Recheck the exact domain in the SURBL Lookup interface linked from the [SURBL FAQ](https://www.surbl.org/faqs).
2. Remove the malicious/spam-advertised resource and correct any sender or hosting compromise.
3. Use SURBL's removal form for the exact listed domain after remediation. Retain the response and timestamp.

### Microsoft SmartScreen

1. Reproduce the warning in a current Edge profile with Defender SmartScreen enabled.
2. Capture the exact warning category and URL.
3. Clean the root cause if valid. If it is a false positive, use the warning's “Report that this site doesn't contain threats” route or Microsoft's site-reporting portal described in its [warning guidance](https://learn.microsoft.com/en-us/troubleshoot/microsoft-edge/development/unexpected-block-warning).
4. Recheck from a fresh profile after Microsoft confirms review.

### Social platforms

1. Use the platform's owner debugger/inspector with the exact rejected URL; do not test by repeatedly publishing posts.
2. Fix redirect loops, unsafe destinations, Open Graph fetch failures, TLS problems, or a genuinely compromised page.
3. Use the platform's appeal/feedback channel and retain the case ID.
4. Verify the exact URL after approval. A social share rejection is not, by itself, a Google or Bing search penalty.

## Traffic diagnosis implication

The verified public negatives make an active Google Safe Browsing warning, Spamhaus DBL entry, or SURBL entry unlikely explanations for current web traffic. They do not close the owner-console gaps. Search visibility, browser safety, email reputation, and social sharing are distinct systems; one cannot be used as proof about another.
