BUILD PROMPT: SYNTHETIC DATA LAB

Build a working, polished web application for designing, generating, inspecting, comparing, validating, and downloading synthetic datasets for data analytics, statistics, simulation, and machine learning.

The defining interaction is this: I choose a data-generating process, change its parameters, and immediately see how the generated data's shape and relationships change. I can then generate a full dataset and download the exact completed result as CSV, together with its configuration, data dictionary, validation report, and optional ground truth.

Act as a senior full-stack engineer, statistical simulation engineer, ML practitioner, and visualization designer. Implement functioning software. Do not stop at a plan, UI mockup, static dashboard, or charts drawn from unrelated hard-coded data.

Read the complete factor inventory in Appendix A. It is part of this specification. Preserve the breadth of that inventory through explicit capability tracking and staged delivery. Do not silently omit a factor because it is mathematically difficult. Do not promise that every factor can be combined with every other factor.

1. PRODUCT EXPERIENCE AND FIRST SUCCESS

Call the application Synthetic Data Lab unless the existing project has an established name. Open directly into a useful example: 5,000 rows, a normal feature, a skewed feature, a categorical feature, and an optional regression target. Show a live histogram, empirical distribution, summary statistics, and a browsable data table without requiring the user to configure everything first.

Provide these workspaces:
- Design: dataset purpose, schema, variable generators, relationships, constraints, and generation pipeline.
- Explore: interactive distributions, joint relationships, time/event views, and the data table.
- Compare: pinned baseline versus current configuration, parameter sweeps, and replicate variability.
- Validate: requested versus achieved properties, violations, statistical diagnostics, and limitations.
- Export: full generation, progress, completed artifacts, and download options.

Use progressive disclosure. Basic mode exposes meaningful common settings. Advanced mode exposes specialized controls. Each setting needs a plain-language explanation, valid range, units where relevant, a sensible default, and immediate validation. Advanced controls must influence the actual generation engine. A disabled capability must explain why it is unavailable.

Use a responsive three-part desktop layout: schema/settings on the left, charts in the centre, and statistics/validation on the right, with a resizable data table below. On narrow screens, turn these into navigable panels. Keep Generate, Resample, Compare, Save configuration, and Download discoverable. Use accessible contrast, keyboard controls, visible focus, labelled inputs, non-colour status cues, and reduced-motion support. Give each chart an accessible text summary.

Make the interface feel like a usable scientific instrument: clear axes, readable numbers, informative tooltips, modest animation, and generous chart space. Avoid decorative dashboard metrics unrelated to the dataset. Technical provenance belongs in an expandable details panel, while the main interface explains what a setting changes.

2. REPOSITORY INTEGRATION AND TECHNICAL APPROACH

Inspect the repository and its instructions before implementation. If this is the suvroghosh-in repository, read docs/architecture/ARCHITECTURE.md and the architecture change gate in CONTRIBUTING.md. Classify the architecture impact before editing. This application may introduce new compute services and expensive endpoints, so it is not routine article publishing. Update architecture documentation and diagrams in the same change, add an ADR for significant decisions, and distinguish implemented safeguards from recommendations in the forensic audit.

Reuse an existing application framework. In an existing SvelteKit project, use SvelteKit and TypeScript. For an empty standalone project, SvelteKit and TypeScript are the default frontend. Use an interactive plotting library with real axes, zoom, hover, brushing, heatmaps, and efficient large-data rendering; Plotly is a reasonable default if its bundle cost is acceptable.

Use Python with NumPy and SciPy for the statistical engine, behind a typed API such as FastAPI. Use pandas or Polars where useful for tabular operations. Add other scientific packages only for a concrete implemented need. Choose compatible stable versions at implementation time and lock dependencies. Do not copy version numbers from the supplied factor inventory without checking them.

Keep the generator a standalone testable Python package, separate from HTTP endpoints and frontend components. Previews, full generation, validation, and CSV output must use the same generation definitions. Do not maintain a simplistic frontend generator with different statistical semantics.

Run expensive work in cancellable workers or jobs. Give the repository a documented local launch command, an example environment file, and a container-based setup when multiple services are needed. If the existing host cannot support the Python worker or long generation jobs, document and implement the separate service boundary. Do not assume that a static frontend or an edge function can execute arbitrary Python workloads.

Use a versioned configuration schema and typed request/response contracts. Prefer a schema-driven capability registry so parameter controls and validation rules cannot drift apart. Keep secrets on the server. For browser-invoked expensive or state-changing endpoints, implement explicit input validation, streamed request-body limits, same-origin checks, timeouts, and rate limits. Preserve applicable repository CSP, security headers, private-cache controls, security audit, and smoke checks.

3. DATASET AND SCHEMA DESIGNER

Capture dataset name, description, intended use, target population, observation unit, number of rows, variables, independent replications, master seed, and output structure. Offer tabular, longitudinal, event, relational, spatial, graph, and survival modes when their respective engines are implemented.

For every field, capture a stable internal ID, column name, meaning, role, type, units, allowed precision, nullability, support, generation rule, dependencies, and export policy. Roles include feature, target, identifier, entity key, group, timestamp, treatment, weight, and diagnostic/ground-truth metadata.

Support continuous and discrete numeric fields; counts; binary values; unordered and ordered categories; dates/times; identifiers; and dictionary/template-based text. Preserve category dictionaries and ordinal ordering. Validate duplicate names and incompatible types. Vector-valued generators must declare all output columns together.

For multiple tables, define each table's row strategy, primary key, foreign keys, relationship cardinalities, and child-count model. Generate keys deterministically without sacrificing uniqueness. Validate cross-table temporal and statistical relationships. Export a data dictionary and machine-readable schema.

Metadata should describe types and relationships explicitly, consistent with the principles in the official [SDV metadata documentation](https://docs.sdv.dev/sdv/integration/metadata). SDV is an optional adapter for fitted synthesis, not a required dependency for user-specified parametric generation.

4. DISTRIBUTION REGISTRY AND PARAMETER CONTROLS

Each distribution adapter must expose its parameter schema, domain checks, support, sampling function, PDF or PMF, CDF/quantiles where available, valid theoretical statistics, and supported fitting methods. Use vetted numerical implementations and explicit conversions from UI parameters. See the official [SciPy statistics reference](https://docs.scipy.org/doc/scipy/reference/stats.html) for available statistical primitives.

Implement these univariate families:
- Normal: mean and standard deviation.
- Uniform: lower and upper bounds; distinguish continuous from discrete uniform.
- Lognormal: log-space mean and standard deviation; optionally accept arithmetic moments through an explicit conversion.
- Exponential: rate or scale, with a clearly selected convention.
- Gamma: shape and rate or scale.
- Beta: two positive shape parameters, with an optional explicitly labelled affine support transformation.
- Weibull: shape and scale.
- Poisson: expected count for a stated exposure interval.
- Bernoulli: success probability.
- Binomial: integer trial count and success probability.
- Negative binomial: an explicit count convention and parameterization.
- Categorical: labels and probabilities.
- Student's t: degrees of freedom, location, and scale.
- Cauchy, Laplace, and logistic: location and scale.
- Pareto: minimum value and tail index.
- Zipf: exponent and any explicit finite-support variant.
- Geometric: success probability and failures-before-success versus trials-until-success convention.
- Hypergeometric: population size, number of successes, and draws.
- Triangular: minimum, mode, maximum.
- Generalized extreme value: shape, location, and scale, with the shape convention documented.

Implement multivariate normal, multinomial, and Dirichlet as multicolumn generators. A multinomial row is a count vector with a fixed total; a Dirichlet row is a probability vector. Neither is an independent scalar generator repeated across columns.

Use unmistakable parameter semantics. Exponential scale is the reciprocal of rate. Standard deviation is not variance. Lognormal log-space location is not its arithmetic mean. For a negative binomial failures-before-r-successes convention, state support and use mean r(1-p)/p; offer mean/dispersion only through a documented conversion. Use the official [negative binomial reference](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.nbinom.html) and [lognormal reference](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.lognorm.html) to verify adapter conventions.

If the UI uses the conventional GEV tail-shape parameter xi, translate it explicitly to SciPy's c = -xi convention. If a truncated-normal UI accepts bounds in data units, convert to the standardized bounds required by the numerical implementation. Check the official [GEV reference](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.genextreme.html) and [truncated normal reference](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.truncnorm.html).

Also implement empirical resampling, histogram distributions, KDE with bandwidth controls, mixtures with component-specific parameters and weights, and subgroup/conditional generators. Add custom discrete masses and validated custom CDF/PDF definitions through restricted declarative expressions or data points. Never execute arbitrary submitted Python or JavaScript. Validate nonnegativity, normalization, CDF monotonicity, support, and numerical integration/sampling error. If a custom sampler only supports bounded support, say so.

Separate these observation mechanisms:
- Truncation: sample from the distribution conditional on an allowed range.
- Censoring: retain an observation bound and an indicator of censoring.
- Clipping: replace values outside limits with boundary values.
- Rounding/quantization: map observations to a specified resolution.
- Zero inflation: add structural zeros to a base distribution.
- Hurdle: generate zero/nonzero status, then sample the nonzero component on its declared nonzero support.

Show the resulting observed distribution after these operations. Do not overlay the original density as if it remained the exact final distribution. Mixtures and clipping can produce mixed discrete/continuous distributions; render their point masses appropriately.

Population parameters and realized sample statistics are different. Provide a separate constrained-sample mode for exact sample means/variances, exact category counts, or fitted quantile targets. Explain the method, feasibility, finite-precision tolerance, and distortion of shape or independence. Arbitrary combinations of exact moments, quantiles, tails, bounds, and dependence may be impossible: reject or explicitly relax them, never silently adjust.

Report an undefined theoretical moment as undefined. Cauchy has no population mean or variance; Student's t, Pareto, and other heavy-tailed distributions have moment-existence conditions. Their finite sample summaries can still be displayed with accurate labels. Specify sample-variance denominator and quantile estimator.

Allow parameter uncertainty distributions, with an explicit draw scope: once per dataset replication, per group, or per observation. These scopes describe different models and must not be interchangeable.

5. DEPENDENCE, SAMPLING, AND REPRODUCIBILITY

Distinguish independence across rows, identical distributions across rows, independence between features, conditional independence, and exchangeability. Display assumptions appropriate to the chosen model rather than one global iid checkbox that overrides everything.

Support independent marginals, multivariate Gaussian dependence, and calibrated copula dependence for supported marginal combinations. Provide target Pearson, Spearman, and Kendall correlations only when their semantics and calibration are implemented. Separate latent copula correlation, requested output correlation, and achieved sample correlation. Include nonlinear and tail dependence through explicitly supported models, without claiming that a correlation matrix describes all dependence.

Validate covariance/correlation dimensions, symmetry, finite entries, variance signs, unit diagonal for correlation, and positive semidefiniteness. Support valid singular matrices where possible. Never silently replace a matrix with a nearby valid one: offer the proposed correction and its size. The covariance requirements are documented in [NumPy's multivariate normal API](https://numpy.org/doc/stable/reference/random/generated/numpy.random.Generator.multivariate_normal.html).

Provide deterministic formulas and conditional generators through an acyclic dependency graph. Reject cycles unless an explicitly implemented joint solver handles them. Add latent factors, informative/redundant/irrelevant features, sparsity, low-rank structures, condition-number targets, clusters, subgroups, nested/crossed groups, random intercepts/slopes, and repeated entities through specialized generator modules. Report achieved quantities when exact targets are not guaranteed.

Sampling modules must cover pseudorandom sampling; replacement rules; exact category allocation; stratification and strata allocation; cluster/multistage sampling; over/undersampling; rare-event and conditional sampling; inclusion probabilities and weights; importance proposals and weights; bootstrap and block bootstrap; antithetic sampling; linear/log/quantile grids; Latin hypercube; Sobol; Halton; and minimum-distance sampling. Clearly distinguish evenly spaced values from random uniform samples. Mark incompatible combinations.

For quasi-Monte Carlo, expose scrambling, dimensionality, and applicable sample-size rules; support coverage/discrepancy diagnostics. See [SciPy's QMC documentation](https://docs.scipy.org/doc/scipy/reference/stats.qmc.html). Do not present QMC points as iid draws or apply iid uncertainty formulas automatically. Bootstrap sampling must have an identified source sample, and dependent data requires an appropriate block/group strategy.

Use an explicit NumPy Generator and RNG algorithm. Derive stable named random streams from the master seed, replication ID, table/variable identity, and mechanism. Do not use process-dependent language hashes or scheduling order as stream identifiers. Use [NumPy's parallel random-stream guidance](https://numpy.org/doc/stable/reference/random/parallel.html). Save stream metadata and RNG state where checkpoint/resume needs it.

Define the reproducibility contract: identical supported configuration, seed, algorithm, dependency versions, execution mode, and logical chunk plan produce the same data. Make logical chunks independent of worker scheduling, or document a narrower guarantee. Do not promise hardware/version independence without implementing and testing it; see [NumPy's compatibility policy](https://numpy.org/doc/stable/reference/random/compatibility.html). Keep generation timestamps outside deterministic data comparisons.

6. TIME SERIES, EVENTS, AND INTERARRIVAL TIMES

Treat event arrivals as a first-class workspace, with process-level controls and event-specific attributes. Support homogeneous Poisson arrivals; renewal processes with exponential, gamma, Weibull, lognormal, deterministic, and validated custom positive interarrival distributions; nonhomogeneous Poisson intensity; and state-dependent arrivals where implemented.

Expose start/end or horizon, time units, rate units, time zone, timestamp resolution, initial-arrival policy, observation-window policy, simultaneous-event policy, independent sequence count, event ordering, and optional entity assignment. Enforce valid positive gaps for simple renewal processes. Handle discretized timestamp ties according to the selected policy, without silently perturbing events.

A homogeneous Poisson process has exponential interarrival times. Poisson counts per interval and Poisson-process timestamps are different output representations. Arbitrary positive iid interarrival times define a renewal process. Time-varying Poisson intensity requires a valid integrated-hazard or thinning algorithm; substituting the current rate into a naive exponential step is insufficient.

Let users choose fixed event count or fixed observation window. Explain that a fixed window generally produces a random count; conditioning on a fixed count within a window is a separate model. Distinguish the initial waiting-time assumption from equilibrium renewal initialization. Keep interarrival time, event duration, service duration, and state dwell time as separate controls. Include event_id, sequence/entity_id, timestamp, elapsed time, interarrival, and relevant attributes in output.

Visualize event rasters, gap distributions, count-by-interval plots, cumulative counts, and intensity where defined. If durations/service are used, show overlapping intervals and implement queue/resource semantics explicitly before displaying queue metrics.

For time series, support regular/irregular sampling, independent sequences, sequence-length distributions, initial conditions, warm-up, trends, seasonality, autocorrelation, cross-series dependence, lagged features, AR/MA/ARIMA-family settings, volatility, regimes, change points, and abrupt/gradual parameter drift through supported model adapters. Validate stability where required and stochastic transition rows. Distinguish Markov state transitions from semi-Markov dwell models.

Treat covariate shift, class-prevalence shift, and concept drift as separate mechanisms. Plot their configured locations and realized effects. Use UTC for internal timestamp calculations with explicit display/export zones and documented DST/calendar rules. ACF/PACF and regular-grid spectral diagnostics require their assumptions; irregular timestamps need appropriate methods or an explicit unavailable state.

7. ML DATASET BUILDER

Provide regression, binary/multiclass classification, multilabel classification, clustering, anomaly detection, forecasting, and survival presets. Every supervised dataset must have an explicit label/outcome generation mechanism and known roles for features, targets, identifiers, and diagnostics.

Regression controls: coefficients/intercept, nonlinear formulas, interactions, effect sizes, response links, irreducible noise, heteroscedasticity, and a precisely defined signal-to-noise measure. Classification controls: prevalence, class-conditional distributions, boundaries/margins, separability, latent probabilities, and class- or feature-dependent label noise. Multilabel controls: label dependencies and co-occurrence. Clustering controls: centres, covariance/shape, size, overlap, subspaces, and manifold geometry where implemented.

Class prevalence and an arbitrary fixed response function cannot always both be prescribed exactly. If an intercept is calibrated to prevalence, report the calibration and achieved frequency. Distinguish structural signal, clean outcome, realized noisy label, and diagnostic probabilities.

Offer train/validation/test splits with random, stratified, grouped/entity, and temporal strategies. Keep duplicate families and repeated entities together where required. Prevent future-derived and target-derived fields from entering feature exports by default. For forecasting, fit transformations on past training observations and generate lag features without looking ahead.

For reference-data fitting, establish allowed splits before fitting distributions, transformations, imputers, encoders, or synthesizers. Fit only permitted training data; reserve held-out data for evaluation. Record synthetic-to-real ratios and synthetic-only versus synthetic-plus-real evaluation designs. Model benchmarks must name the metric, split strategy, and task, and must not claim usefulness on an unknown real-world problem solely from synthetic test performance.

Export ordinary model features/targets separately from optional latent variables, clean outcomes, anomaly labels, causal truth, and corruption metadata. Ground-truth availability is valuable for benchmarking but must not create accidental model leakage.

8. NOISE, MISSINGNESS, ANOMALIES, AND DATA QUALITY

Provide a visible, ordered generation pipeline. A typical pipeline is latent/entity structure -> clean features -> clean outcome mechanism -> observation noise -> anomalies/corruptions -> missingness/censoring -> duplicate generation -> split-aware export. Some models need another order. Make the actual order explicit, validate dependencies, and record it in the configuration. Reordering operations must regenerate and revalidate the result.

Support additive/multiplicative measurement and process noise; systematic bias; constant or feature-dependent variance; correlated errors; temporal/spatial correlation where supported; and magnitude or signal-to-noise controls. Identify whether noise affects the observed feature, outcome, or latent process.

Support per-column and per-subgroup missingness rates with MCAR, MAR, MNAR, structural missingness, correlated masks, monotone dropout, intermittent observations, and missing timestamps. Let users choose probabilistic rates versus exact allocated counts where feasible. MAR rules may depend on explicitly available observed information; MNAR can depend on values that become unobserved. Explain these mechanisms in context and show achieved rates. Missingness indicator columns must be optional and clearly named.

Support injected point, contextual, and collective anomalies with mechanisms, magnitudes, locations, and proportions. Keep naturally occurring tail observations distinct from injected anomaly labels. Include duplicates, near duplicates, typos, category miscoding, inconsistent formatting, and explicitly chosen invalid-value injection.

Keep clean and observed/corrupted versions separate internally. Optional paired exports must join through stable identifiers. Report intended invalid injections separately from unintended validity failures; never silently repair intentional corruption or treat an unintentional key violation as an injected anomaly.

9. CONSTRAINTS AND FEASIBILITY

Implement constraints on ranges, nonnegativity, integers, allowed/forbidden category combinations, conditional rules, sums and percentages, probability simplexes, monotonicity, field inequalities, chronological order, keys, cardinalities, units, checksums, locale formats, and domain/physical plausibility.

Provide declarative formulas for derived columns and constraints, with a safe allowlisted expression parser. Validate expression size, dependency depth, allowed operations, and computational cost. No eval, shell execution, unrestricted imports, filesystem access, or network calls from user-defined expressions.

Detect contradictions before generation where possible. Explain an infeasible rule using the affected fields. Let the user explicitly choose any proposed relaxation. Prefer generation by construction; use bounded rejection or documented projection/repair only when appropriate. Set retry, time, and acceptance limits. Failed constraints must not cause an infinite loop.

Report attempted and accepted rows, rejection causes, repaired values, violations, and resulting distribution distortion. A dataset must not be labelled valid merely because its unconstrained latent values had the requested distribution. Clarify which rules apply to clean data and which apply to observed/corrupted data.

10. ADVANCED DOMAIN MODULES

Implement these as real modules in later stages, with clear capability boundaries and domain-specific diagnostics. Their existence in the schema is not proof of working support.

Causal simulation: user-specified DAGs, structural equations, observed/latent confounders, mediators/moderators, treatment assignment, interventions, heterogeneous effects, selection/inclusion mechanisms, and counterfactual scenarios. State the assumed structural model. Correlations and fitted reference data do not establish causal direction. Paired counterfactuals must preserve the appropriate unit-level exogenous variables.

Survival: event-time distributions, baseline hazards, covariate effects, competing risks, dropout, delayed entry where supported, and censoring. Export observed times, event indicators/types, and optional latent event times. Provide survival/cumulative-incidence views appropriate to the model; do not confuse censoring with truncation or silently use ordinary survival estimators for incompatible designs.

Spatial/spatiotemporal: dimensions, coordinate reference system, boundaries, point intensity, clustering, covariance kernel, correlation length, anisotropy, edge effects, trajectories, movement limits, and temporal dependence. Use distance units compatible with the coordinate system. Do not apply Euclidean kilometre-based kernels directly to longitude/latitude degrees.

Graphs: node/edge counts, directedness, self-loop/multiedge policy, degree models, communities, connectivity, weights, attributes, and evolution. Validate feasible edge counts and degree specifications. Export nodes and edges separately with stable IDs and provide bounded-size network views.

Relational/longitudinal: multiple tables, per-parent child counts, cardinalities, shared latent effects, nesting/crossed groups, repeated measures, within/between-group variation, intraclass correlation, and cross-table time/dependence rules. Validate referential integrity and prevent entities from leaking between protected data splits.

Text: dictionary/template-based synthetic strings with locale/language, vocabulary version, length models, formatting, and consistency with structured fields. Do not claim rich semantic synthesis if the implementation only samples unrelated words. Any optional language-model backend must be separately configured and must not receive reference records without an explicit user action and documented data handling.

11. LIVE VISUALIZATION AND PARAMETER EXPLORATION

Changing a valid parameter should trigger a debounced preview, approximately 150-300 ms after editing stops, followed by a visible updating state if needed. Keep inputs responsive while generation runs. Use request cancellation and monotonically versioned configuration IDs so an older response cannot replace a newer chart.

Default preview size: 5,000 rows, adjustable within declared resource limits. Display preview size and requested full size separately. Use a stable seed while editing; provide a distinct Resample action. Where supported, use common random numbers/inverse transforms for parameter comparisons so random redraw noise does not obscure shape changes. Do not promise pointwise smoothness for discrete, rejection-sampled, or structurally changing models.

A smaller preview cannot automatically satisfy full-dataset exact category counts, relational cardinalities, event horizons/counts, or other global constraints. Define an explicit preview policy for each module: a bounded realization with an effective preview configuration, a labelled subset of a completed realization, or a full-generation-only mode. Record and display any changed counts, allocation, or time window. Preserve whole entities/relationships where needed. Mark full-only checks not evaluated in the preview. Never silently change the model or claim full-dataset constraint compliance from a small preview.

All panels must display the same configuration version and result ID. Charts, table rows, statistics, and validation must not silently show different generations. Switching views or sorting a table must not regenerate the data. If a configuration changes after full generation, mark the completed result as belonging to the earlier configuration until a new job completes.

Implement linked visualizations appropriate to the selected variables:
- Numeric: histogram with adjustable bins, optional density overlay, ECDF/CDF, quantile plot, box/violin view, and robust summaries.
- Discrete/categorical: counts/proportions, PMF where appropriate, category ordering, and contingency views.
- Pairs/multivariate: scatter/hexbin, selected scatter-matrix panels, Pearson/Spearman/Kendall matrices where defined, subgroup facets, and pairwise sample counts under missingness.
- ML: class balance, boundaries for suitable low-dimensional examples, feature/target relationships, residuals, and benchmark calibration when computed.
- Temporal/event: timeline, line plots, ACF/PACF when appropriate, seasonality/drift views, arrival rasters, gaps, interval counts, and cumulative events.
- Data quality: missingness matrix, subgroup missingness, corruption/anomaly overlays, and clean-versus-observed comparisons.
- Advanced modes: survival, spatial, graph, and relational views provided by their implemented modules.

Show theoretical and empirical curves as distinct layers. Use histogram density when comparing to a PDF and probability masses when comparing to a PMF. An estimated KDE is not a theoretical density. Include observed-space transformations in overlays when mathematically available; otherwise label the overlay as a base-model reference or unavailable.

Offer fixed/shared axes, bin edges, bandwidth, and linear/log scales so before/after comparisons are meaningful. Handle zero and negative values explicitly on log scales. Preserve unsmoothed empirical views. Display plot sampling/downsampling and the exact rows or selection policy used. Large scatter plots may use deterministic samples or density aggregation; full-result summaries must not be presented as if calculated from all rows when they are sampled.

Provide a baseline pin and side-by-side/overlay comparison with a parameter-difference panel. Add parameter sweeps: select one parameter, range, step count, replicate count, and fixed versus fresh random streams. Show shape evolution and metric-versus-parameter plots. Animation needs play/pause, speed, reduced-motion support, and resource limits. Distinguish uncertainty across independent replicates from a sequence of slider positions.

Data-table features: virtualized rows, sorting/filtering, column roles/types, null representation, and clearly identified sampled views. Brushing should update linked views using a documented subset, without pretending that the selection changes the underlying generating distribution. A filtered/selected export must be an explicit export choice.

12. VALIDATION, FITTING, AND PRIVACY

Validate at three levels: configuration feasibility, generated-data integrity, and statistical/model fidelity. Use statuses such as pass, fail, warning, not applicable, and not evaluated. Unsupported or uncomputed checks must never appear as passing.

For each applicable check, report target, achieved value, tolerance, sample size, relevant uncertainty, and interpretation. Include marginal and conditional distributions, quantiles/tails, joint dependence, subgroup representation, temporal/spatial dependence, effective sample size where meaningful, constraints, exact counts, keys, leakage checks, and downstream task metrics. Record pre- and post-corruption checks separately.

Use suitable distributional distances and diagnostic tests for continuous, discrete, categorical, dependent, and fitted models. Do not apply the ordinary continuous KS null distribution blindly to discrete data or parameters estimated from the same sample. Large samples can flag tiny differences; accompany tests with effect sizes and plots. A goodness-of-fit p-value is not the probability that a model is correct. Account for dependent observations and multiple checks where needed. Monte Carlo intervals must state their method and assumptions.

Reference data is optional. Accept a bounded CSV upload, show inferred schema for review, and allow explicit fitting subsets and candidate distributions. Record fitting method, parameter estimates, source metadata, representativeness concerns, and held-out diagnostics. Include reference summary-statistics-only input when feasible. Never quietly train on validation/test records or upload reference data to an external service.

Reproducing reference-fitted, empirical, or KDE generation also requires the frozen fitted state or the same permitted source data. Version and hash that state, including preprocessing and category dictionaries. Treat fitted artifacts, empirical samples, and KDE centres as potentially sensitive; apply access, retention, deletion, and export controls to them. Record a protected source/model dependency when it cannot safely be bundled. Configuration plus seed alone must not be advertised as sufficient for these modes.

Separate two workflows: generating from user-specified hypothetical models, and learning a generator from potentially sensitive real data. Synthetic output learned from real records is not automatically anonymous or private.

For fitted synthesis, implement clear local/server processing disclosure, retention controls, deletion, sensitive-field handling, and no raw-record logging. Exact/near-copy, membership-inference, attribute-inference, and linkage-risk assessments are separate diagnostics with specified threat models; an unrun assessment is not a passed check.

If formal differential privacy is implemented, require a supported mechanism, privacy unit/adjacency definition, clipping/bounds, epsilon/delta, accountant, budget composition across releases, and an auditable training/release path. A private deployment must also account for previews and diagnostics that access real data. Do not offer a working-looking DP toggle, privacy score, or privacy guarantee before this exists. Clearly report unsupported privacy requirements. Implementing ordinary parametric generation does not require pretending that a DP mechanism is present.

13. DOWNLOADS, CONFIGURATIONS, AND PROVENANCE

Make CSV the primary output. Generate an immutable result first, then export that exact result without resampling. A Download preview action exports the exact preview with a clear preview label; Download full dataset exports the completed full job. Do not silently replace one with the other.

Use UTF-8 and correct CSV quoting/escaping, configurable delimiter and null representation, explicit column order, numerical precision, and documented timestamp/time-zone serialization. Preserve category labels unless encoded output is explicitly requested. Detect ambiguous null sentinels and nonfinite values. Avoid locale-dependent decimal formats by default. Never silently turn valid numeric negatives into strings for spreadsheet safety.

Offer an explicitly labelled spreadsheet-safe mode for string cells that could be interpreted as formulas, with transformations recorded. Raw analytics CSV should preserve intended data values. Test commas, quotes, line breaks, Unicode, timestamps, categorical values, and empty versus missing strings.

For multiple tables, replications, splits, or large partitions, provide a ZIP with clearly named CSV files and a manifest. Include these companion artifacts:
- configuration.json: complete validated settings, schema version, seeds, sampling modes, mechanisms, ordering, and transformations.
- schema.json and data_dictionary.csv: column meanings, types, roles, units, relationships, and missing-value conventions.
- validation_report.json: machine-readable checks, failures, warnings, tolerances, and uncomputed checks.
- summary_statistics.csv or JSON: actual output summaries and subgroup/temporal diagnostics.
- generation_manifest.json: generator/dependency versions, configuration digest, result ID, timestamps, stream allocation, row counts, split membership policy, file checksums, and reference provenance without embedding private source records.
- Optional ground_truth/ files: structural parameters, latent variables, clean values, class probabilities, anomaly/corruption masks, and causal quantities selected by the user.
- A runnable Python reproduction script that uses the same engine/configuration rather than a simplified approximation, together with any approved fitted-state artifact or explicit instructions for supplying the protected model/source dependency. If a required dependency has been deleted or cannot be released, label the bundle as not self-contained for reproduction.

Allow configuration import/export, presets, and saved local experiments. Use stable configuration hashes with a documented canonicalization strategy. Record the actual generated seed even when the user asks for a fresh seed. An imported configuration must be version-migrated or rejected with an actionable message.

Support gzip/ZIP compression and Parquet as optional extras after correct CSV support. Define batch sizes, output partitions, file limits, stable IDs across batches, incremental append semantics, and checkpoint/resume where supported. Some global constraints prevent independent streaming: label or reject these combinations instead of falsely claiming arbitrary batch equivalence. Partial or failed jobs must not masquerade as completed datasets.

  temporal/event/spatial/graph/causal/survival: applicable typed module configs
  outcomes: task, function, coefficients, probabilities, label_noise
